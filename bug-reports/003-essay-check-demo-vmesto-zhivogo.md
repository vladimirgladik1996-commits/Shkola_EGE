# 003 · ИИ-проверка: разбор выдаётся демо-данными, фото не уходят в ИИ (APK/мини-апп)

Статус: **причина найдена** — исправление в окружении сервиса (см. §4), код не требует правок.
Дата: 2026-10-24. Раздел «ИИ-проверка». Доказательства: `003-scrin-1.jpeg`, `003-scrin-2.jpeg`.

---

## 1. Симптомы (как их видит пользователь)

Пользователь сфотографировал рукописную работу (конспект про вакансии/резюме) и получил разбор:

1. **Красный баннер на экране разбора:** «⚠ Демо-режим: разбор демонстрационный,
   фото не отправлялись в ИИ» (`003-scrin-1.jpeg`).
2. **Ошибки — заглушки, их нет на фото.** В разборе значатся «влеяния», «в течении»,
   «Во первых», «более лучше», «по этому», «Таким образом автор» — слова из демонстрационного
   сочинения о книге, которых на снимке ученика нет вовсе.
3. **Маркеры ошибок съехали** — пины (№1, 3, 4, 5, 6, 7) стоят скоплением внизу снимка,
   а не над словами-ошибками (`003-scrin-2.jpeg`).

Ожидаемое поведение: фото уходят в Yandex Vision OCR + Кими, ошибки находятся по реальному
тексту ученика, маркеры стоят над словами-ошибками, баннера «Демо-режим» нет.

## 2. Причина (точные адреса в коде)

**Сервис запущен в демо-режиме: в процессе не выставлен `EC_LIVE=1`.**

`prod/bot-mini-app/essaycheck.py` (и зеркально `dev/…`), строка 28:

```python
DEMO = os.getenv("EC_LIVE", "").strip() != "1"   # выключается только командой владельца (EC_LIVE=1)
```

Демо-режим **включён по умолчанию** и выключается только точным значением `EC_LIVE="1"`
(`"0"`, `"true"`, пусто — всё остаётся в демо). Пока `DEMO` истинно, `run()` (строка 351)
вообще не ходит в API:

```python
if DEMO:                                   # фото не уходят в API — только локальный демо-разбор
    async for ev in _demo(w, t):
```

`_demo()` (строка 205) возвращает `_result({"errors": DEMO_ERRORS, …})` и ставит `res["demo"] = True`
(строка 219) — фронт по этому флагу показывает баннер «Демо-режим»
(`docs/index.html`, строка 3137).

Цепочка на скринах: «Готово» → upload/`run` → `essaycheck.DEMO == True` → `_demo()`
→ на **настоящие** фото ученика натягиваются `DEMO_ERRORS` со своими демо-координатами
`page/x/y` (строки 40–60: 7 ошибок, «влеяния», «в течении» и т.д., взятые из макета
`dev/mockups/essay-check.html`) → координаты, вычисленные для другого изображения, не
совпадают с текстом ученика и пины оказываются внизу снимка. Это **тот же визуальный баг,
что и в 001**, но источник моков теперь не фронт (`EC_MOCK` уже `false`, строка 2848 index.html),
а бэкенд-демо.

**Почему `EC_LIVE` не действует.** В `render.yaml` переменная объявлена (`- key: EC_LIVE`,
`value: "1"` для обоих сервисов), но:

- **`YANDEX_API_KEY` отсутствует в blueprint вообще** — в `envVars` сервиса его нет
  (в комментарии лишь сказано «вводится в панели Render»). Даже с `EC_LIVE=1` боевой пайплайн
  без него не стартует: `bot.py:2645` отдаёт `{"t":"off"}` (фронт покажет «off», а не разбор).
  То есть окружение сервиса просто не доведено до боевого.
- Переменные с `sync: false` вводятся вручную при синхронизации blueprint — пока значения
  не введены, изменения `tutor-bot` не применяются (об этом же предупреждение в конце
  `render.yaml`). Синхронизация могла не пройти, и в сервисе живут старые env.
- На варианте деплоя через `deploy.sh` + `docker-compose.yml` (env из `.env`) в
  `.env.example` по умолчанию стоит `EC_LIVE=0` (строка 96) — копия примера даёт демо.

**Почему это не покрыто тестами.** `tests/test_apk_shell.py:34` как раз и охраняет этот
случай (`"Демо-режим" not in html`), но сейчас он **падает**: после коммита `bfb41e0`
баннер «Демо-режим» осознанно добавлен в `docs/index.html` (строка 3137), а тест не обновлён —
регрессионный контракт в красной зоне и не защищает от подмены данных демо-режимом.

## 3. Что подтвердило диагноз

- На скриншотах баннер «фото не отправлялись в ИИ» — это прямой вывод `result.demo === true`,
  который ставит только `_demo()` (строка 219).
- Тексты ошибок буквально совпадают с `DEMO_ERRORS`/`DEMO_TEXT` из `essaycheck.py`
  («влеяния», «в течении», «Во первых», «более лучше», «по этому») — на фото ученика
  (конспект про вакансии) этих слов нет.
- Локальный прогон: `EC_LIVE='' / '0' / 'true' → DEMO=True`, `EC_LIVE='1' → DEMO=False`.
- `EC_MOCK=false` в `docs/index.html` — фронт-мок отключён, значит источник демо-данных — бэкенд.
- `python3 tests/test_apk_shell.py` → `AssertionError: dev: демо-данные не должны подменять
  реальные` (контрактный тест красный).

## 4. Исправление

Код менять не нужно — требуется довести окружение сервиса:

1. Render Dashboard → `tutor-bot` (и `tutor-bot-dev`) → Environment:
   `EC_LIVE=1` (строго «1»), `YANDEX_API_KEY` (ключ Yandex Cloud с ролью `ai.vision.ocr.user`),
   `KIMI_API_KEY` — и перезапустить сервис.
2. В `render.yaml` добавить `YANDEX_API_KEY` в `envVars` обоих сервисов (`sync: false`),
   чтобы blueprint перестал его терять.
3. Поправить регрессионный контракт `tests/test_apk_shell.py:34`: проверять не саму строку
   «Демо-режим», а то, что страница не подменяет данные моком (`EC_MOCK=true`, `demoData`),
   либо исключить из проверки строку с баннером — тест снова зелёный и защищает от 001/003.
4. Вариант деплоя через `docker-compose`: в `.env` выставить `EC_LIVE=1` (в `.env.example`
   оставить `0` — это безопасный дефолт, но явно задокументировать).

## 5. Проверка после исправления

- Повторить сценарий со скринов: на экране разбора **нет** баннера «Демо-режим»,
  тексты ошибок совпадают с текстом на фото, пины стоят над словами-ошибками.
- `python3 tests/test_apk_shell.py` → `OK`.
- В логах сервиса: `essay check: tg_id=… photos=…` и стадии OCR/Kimi, а не мгновенный демо-разбор.
