# 011 — Word-файлы «Чата с ИИ» не открываются на Samsung («Файл повреждён») и без красной строки

Пользователь прислал реальный пример (`Сочинение_рассуждение_133_ОГЭ_2027_по_тексту_Е_И_Носова.docx`)
и скриншот: мобильный Word на Samsung отвечает **«Не удается открыть файл. Файл повреждён.»**.
Второй баг того же файла: **в абзацах нет красной строки** (отступа первой строки) — текст идёт «в край».

---

## 0. Корень: рукотворный XML против строгих просмотрщиков

Word-файлы чата собираются без библиотек — `chatfiles.docx_bytes()` шьёт ZIP с XML-частями руками.
Пока XML точно соответствует схеме OOXML (ECMA-376), всё открывается. Было три нарушения:

1. **Порядок элементов внутри `w:rPr`** — `w:u`/`w:b`/`w:i`/`w:rFonts`/`w:sz`/`w:color` шли не по схеме.
   Исправлено 24.10 (`9094aaa9`).
2. **«Голые» `<w:p>` в `<w:tr>`** вместо `<w:tc>` — строки таблицы без ячеек, прямое нарушение схемы.
   Исправлено 25.10 (`90552c71`).
3. **Абзацы без красной строки** — `w:ind w:firstLine="709"` (1.25 см) не ставился.
   Исправлено 25.10 (`e0d63abf`).

Почему баг виден только на части устройств: **десктопный Word и мягкие просмотрщики молча чинят
такой файл при открытии**, а строгие парсеры (мобильный Word на Android, Samsung) валидируют схему
и объявляют файл повреждённым.

## 1. Присланный файл — доказательство

Валидация по официальной схеме `wml.xsd`:

```
FAIL word/document.xml — Element 'w:p': This element is not expected. (×6 — строки таблицы)
PASS word/styles.xml / settings.xml / header1.xml / footer1.xml
```

Состав файла точно соответствует билду **между** фиксами `9094aaa9` и `e0d63abf`
(порядок `w:rPr` уже верный, красной строки ещё нет, таблицы ещё без `<w:tc>`) — то есть
документ сгенерирован сервером в окне деплоя 25.10 ~03:54–04:11. Старые файлы остаются
сломанными навсегда: они лежат у пользователей, сервер их не пересобирает.

## 2. Что сделано этим фиксом

* **`tests/test_docx_ooxml.py` (dev + prod)** — регресс-тест генератора Word:
  * порядок дочерних элементов по схеме для `w:rPr`/`w:pPr`/`w:sectPr`/`w:tblPr`/`w:trPr`/`w:tcPr`/
    `w:tblBorders`/`wp:inline`/`wp:anchor`/`pic:pic`;
  * в `<w:tr>` — только `<w:tc>`, в ячейке — минимум один `<w:p>`;
  * текстовые абзацы — с красной строкой `w:ind w:firstLine="709"`;
  * `[Content_Types].xml` покрывает все части пакета и не объявляет несуществующих;
  * каждая часть — валидный XML без запрещённых символов (`_BAD_XML`);
  * **негативные проверки**: тест ломает файл ровно как старый генератор и требует,
    чтобы проверки его поймали — иначе тест «зелёный» ничего не держит.
* **`chatfiles.py` (dev + prod)** — остатки, которые нашёл тест:
  * `[Content_Types].xml` больше не объявляет `/word/header2.xml`, когда фирменная шапка
    не кладётся в пакет (Override на несуществующую часть — грязь для строгих проверок);
  * маркер списка и текст больше не склеиваются («•Текст» → «• Текст», неразрывный пробел).

## 3. Проверка

```
python3 tests/test_docx_ooxml.py     # dev и prod: 6 проверок, все зелёные
```

Существующие `tests/test_chat_files.py` и `tests/test_essay_report.py` не задеты
(в песочнице часть шагов падала только из-за отсутствующих `xhtml2pdf`/`aiohttp` — к коду не относится).

## 4. Что делать со старыми файлами у пользователей

Перегенерировать: старый .docx собран старым кодом и не «лечится» на сервере. Карточки файла
в чате пересобираются уже новым кодом (`api_chat_file_rebuild`).
