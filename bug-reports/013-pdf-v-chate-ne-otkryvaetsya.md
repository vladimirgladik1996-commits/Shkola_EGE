# 013 · Чат с ИИ: PDF-документ не открывается и не скачивается

**Дата:** 2026-10-26
**Раздел:** Чат с ИИ
**Статус:** ✅ исправлено (часть 1 — фронтенд, часть 2 — бэкенд)

## Симптом

В разделе «Чат с ИИ» модель собирает PDF, в чат приходит карточка файла
(иконка PDF, название, «PDF-документ · открыт», кнопки **«⤓ Скачать»** и
**«🔗 Поделиться»**). Кнопки кликабельны, вёрстка целая — но **документ не
открывается и не скачивается**: тап не даёт никакого видимого эффекта.

При этом **«Скачать АПК»** из нижнего меню работает. Разница между двумя
путями — единственная зацепка, которая и привела к причине.

## Причина

Три независимых дефекта, действовавших вместе.

### 1. `tg.openLink` вызывался после `await` — Telegram его молча игнорировал

`docs/index.html`, `chOpen()`:

```js
async function chOpen(i,j){const x=await chFresh(i,j);   // ← сетевой POST, r
  ...
  if(!APP&&tg&&tg.openLink){tg.openLink(u);return true}  // ← уже вне user-gesture
```

`tg.openLink` честно обрабатывается Telegram **только синхронно в ответ на тап**.
Любой `await` перед вызовом — даже просто запрос за свежей ссылкой — выносит вызов
из user-gesture, и клиенты его **молча игнорируют**. Ни ошибки, ни тоста: тап
просто «не делает ничего».

Именно поэтому «Скачать АПК» работал: `apkDl()` зовёт `tg.openLink(u)` **без
`await` перед вызовом**, а `chOpen()` — с `await`. Один и тот же вызов, разный
контекст.

### 2. Ссылка умирала за 30 минут

Файлы чата живут в памяти процесса (`EC_CHECKS`, `EC_PHOTOS` — словари), срок
подписи — `EC_TTL = 30*60` («полчаса, как подписные ссылки файлов чата»).
Render перезапускает сервис, и тап по старой карточке вёл на протухшую ссылку.
`chFresh()` как раз и собирал файл заново — но становился причиной №1.

### 3. `Content-Disposition: attachment` мешал показу

`bot.py` отдаёт файл с `attachment` — браузер молча скачивает PDF вместо того,
чтобы открыть его просмотрщиком.

## Исправление

**Часть 1 (фронтенд) — этот коммит, dev+prod, `docs/index.html` идентичны:**

- `chOpen()` стал синхронным в своей части, которая трогает Telegram: между тапом
  и `tg.openLink(u)` **нет ни одного `await`**. `chOpen` больше не `async`;
- свежая ссылка подогревается **в фоне**: `chRefresh(i,j)` вызывается уже **после**
  синхронного открытия и кладёт новую ссылку обратно в карточку (`chPut`) —
  следующий тап открывает файл сразу;
- `chPrefetch()` — прогрев ссылок на файлы карточек чата (с защитой от повторов
  чаще раза в минуту);
- порядок веток открытия сохранён: APK (`openFile`) → старый APK → Telegram
  (`openLink` → `downloadFile`) → браузер (`<a download>`).

**Часть 2 (бэкенд) — этот коммит, dev+prod, `bot.py` идентичен:**

- файлы чата теперь живут **на постоянном диске**, а не только в памяти процесса:
  таблица `chat_files` в `tutor.db` (миграция v5), путь тот же, что у базы
  (`DATA_DIR`, на Render это смонтированный диск 1 ГБ). Память — быстрый путь,
  диск — страховка от рестарта;
- `chat_file_load()` — чтение «память → диск» с обратной подкладкой в память;
  `chat_file_drop()` и `chat_file_set_fid()` пишут в оба места;
- `Content-Disposition` разведён по назначению (`chat_file_disposition()`):
  `pdf`/картинки → `inline` (просмотрщик показывает), остальные (`docx` и т.п.) →
  `attachment`; `?dl=1` форсирует скачивание для любого типа;
- устаревшая подпись в `api_chat_file` («файл живёт полчаса») приведена к факту — сутки.

Что осталось за рамками 013 (в отдельных задачах): `EC_CHECKS`/`EC_PHOTOS` —
сеансы «ИИ-проверки» — по-прежнему живут в памяти процесса.

## Проверка

`tests/test_pdf_open_link_sync.py` (dev+prod):

- `chOpen()`: `tg.openLink` идёт **до** первого `await` — ловит регресс
  (до фикса тест красный: `openLink` на позиции 262, первый `await` — на 8);
- `chDl()` («Скачать») идёт через `chOpen()` — единый путь открытия;
- `apkDl()`: «Скачать АПК» остаётся синхронным — страж против той же поломки;
- есть запасной путь (`downloadFile` / `<a download>`), если `openLink` недоступен.

Плюс `tests/test_frontend_contract.py` (27 вызовов `api()` совпадают с методами
маршрутов) и `node --check` по инлайн-скриптам — JS не сломан.

`tests/test_chat_file_persist.py` (dev+prod), до фикса красный — падал на
«файл НЕ пережил рестарт: status=404»:

- файл находится после «рестарта» (сброса `CHAT_FILES` при целом диске);
- PDF без `?dl=1` → `inline`, с `?dl=1` → `attachment`;
- `docx` → `attachment` в обоих режимах, `png` → `inline`;
- чужой `tg_id` → 403 даже с действующей подписью;
- без подписи / с мусорной подписью → отказ, не 200.
