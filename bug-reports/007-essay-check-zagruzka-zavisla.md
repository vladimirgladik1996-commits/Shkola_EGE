# 007 · ИИ-проверка: «долгая загрузка» фото и зависание по нажатию «Готово»

Статус: **исправлено** — см. §4 «Исправление».
Дата: 2026-10-24. Раздел «ИИ-проверка». Прод: `tutor-bot` (Render, `prod/bot-mini-app`).
Затронуты обе копии кода: `dev/` и `prod/`.

---

## 1. Симптомы (как их видит пользователь)

1. На экране съёмки фотографируешь страницы работы, жмёшь «Готово» — и экран **долгую
   загрузку** висит без каких-либо признаков жизни: ни прогресса, ни текста, ни кнопки.
2. В какой-то момент — **зависание навсегда**: ни перехода на экран проверки, ни ошибки,
   ни «Повторить». Кнопка «Готово» перестаёт реагировать, выйти можно только «Назад»
   и начать всё сначала. Повтор — то же самое.

## 2. Что показали логи прод-сервиса (Render, `tutor-bot`)

Разобраны логи `srv-db6eg0ajnfac73dfqv5g` за 22–24.10 (API Render `GET /v1/logs`):

- **падений и исключений в бэкенде НЕТ** — только шум: переподключения long-polling
  Telegram (`Connection reset by peer`) и `SIGTERM` при деплоях (перезапуски сервиса
  в среднем раз в 1–2 часа);
- успешные прогоны проверки идут **3–5 минут** (например, 24.10: `run` стартовал в
  07:22:43 и завершился в 07:27:37 — почти 5 минут, 466 КБ событий стрима);
- **24.10 после деплоя в 08:40 UTC запросов `/api/essay_check/upload` и `/api/essay_check/run`
  в логах НЕТ вовсе** — хотя пользователь в это же время пробовал проверку и видел зависание.
  Значит, запрос загрузки фото **не дошёл до конца даже на сервере**: тело запроса (несколько
  МБ base64) переставало отправляться, соединение висло, `aiohttp.access` (пишется по
  завершении запроса) не появлялся;
- 23.10 в 17:14–17:22 — всплеск `403 api denied` на `/api/essay_check/upload` с
  `Python-urllib/3.12` (посторонний скрипт без входа), к багу отношения не имеет.

То есть «зависание» — **не серверное**: бэкенд здоров, виснет клиентская загрузка фото.

## 3. Причины (точные адреса в коде)

Симптом «долгая загрузка + зависание» давала связка из трёх вещей на шаге «Готово».

### 3.1. Все фото уходили ОДНИМ тяжёлым запросом прямо по «Готово»

`docs/index.html`, `ecUpload()` (до исправления):

```js
const pack=a=>a.map((d,i)=>({n:"photo-"+(i+1)+".jpg",d:d.split(",")[1]||"",...}));
const r=await api("/api/essay_check/upload",{w:pack(ecShots.w),t:pack(ecShots.t)});
```

До 12 фото по ~300–700 КБ base64 = **3–10 МБ JSON одним POST**. На мобильной сети
(3G/нестабильный LTE) его отправка занимает минуты — отсюда «долгая загрузка». При этом
фото уже лежат на телефоне с момента съёмки, и ждать их отправки в момент «Готово» вообще
не нужно: перенос на сервер можно начинать сразу после снимка.

### 3.2. Загрузка шла через `api()` → `fetch()` без таймаута — зависала навсегда

`docs/index.html`, `api()`: `fetch()` и чтение ответа жили **без единого потолка времени**.
Мёртвая сеть (уснувший телефон, оборванный TCP без FIN, нестабильный мобильный интернет)
вешала промис вечно: запрос не завершался ни успехом, ни ошибкой. Пока он висел,
`ecBusy=true` держал кнопку «Готово» заблокированной — «зависание навсегда».

Это тот же класс, что починен для стрима в `bug-reports/005` (§2.2), но для обычных
запросов таймаут тогда остался «отдельным инцидентом» (§5 отчёта 005) — вот он.

### 3.3. Никакой обратной связи о ходе загрузки

Во время отправки экран не менялся в принципе: ни прогресса, ни статуса, ни возможности
отличить «медленно, но идёт» от «умерло». Даже честно работающая загрузка выглядела как
зависание — и это «выглядело» было неизбежным при архитектуре «всё одним запросом на
кнопке».

## 4. Исправление (dev и prod синхронно)

**Главное по ТЗ: фото уходят на сервер СРАЗУ после съёмки или выбора из галереи —
по одному, фоном. «Готово» лишь проверяет набор фото (окна задания/работы — как раньше),
собирает проверку уже из загруженных фото и стартует проверку МГНОВЕННО.**

**`bot.py` — новая копилка фото и мгновенная сборка сеанса:**
- `POST /api/essay_check/photo` — одно фото `{sid, set:"w"|"t", n, d, mime}` сразу после
  снимка: нормализация в JPEG ≤1600 px (PIL в потоках, как раньше), кладётся в копилку
  сеанса `sid`, ответ `{"id": pid}`; лимит `EC_MAX_PHOTOS`, TTL копилки — час;
- `POST /api/essay_check/upload` теперь принимает **`{sid, w:[pid], t:[pid]}`** — лёгкий
  запрос, сеанс собирается из уже загруженных фото **с сохранением порядка**; прежний
  формат `{w:[{n,d,mime}],…}` («всё сразу одним запросом») сохранён для прежних сборок APK;
- чужое/протухшее фото → честный `400 {"error":"gone"}` — клиент перезальёт фото заново.

**`docs/index.html` — загрузка фоном и мгновенный «Готово»:**
- `ecUpApi()` — POST через XHR с **прогрессом отправки**: сторож тишины `EC_UP_IDLE` (30 с)
  перезапускается каждым прогрессом — медленная, но живая сеть НЕ убивается, а мёртвая
  обрывается за 30 с (а не висит вечно); общий потолок `EC_UP_MAX` (90 с) на фото;
- `ecUpOne()`/`ecUpKick()` — фото уходит на сервер сразу после `ecCamShot`/`ecPicked`;
  повторные снимки грузятся параллельно, один запрос на фото; сбой фото не мешает съёмке;
- «Готово» (`ecUpload`): валидация фото задания/работы (окна `ecAskWork`/`ecAskTask` — без
  изменений) → дозагрузка неотправленного (обычно пусто) → сборка сеанса по id →
  **сразу** экран проверки и `ecRun()`; потеря фото сервисом (перезапуск — их логи выше!)
  обрабатывается честной перезагрузкой фото и повторной сборкой;
- `api()` получила `opt.idle` (AbortController — зависший запрос прерывается и возвращает
  `null`, как HTTP-ошибка) и `opt.silent` (вызывающий код сам объясняет причину).

## 5. Проверка

- `tests/test_essay_photos.py`:
  - контракт фронта: фото уходит сразу после съёмки/галереи (`ecUpKick`), сторож тишины
    перезапускается прогрессом отправки, «Готово» собирает сеанс по id и сразу стартует
    проверку, тяжёлый запрос «всё сразу» с фронта убран, окна задания/работы сохранены;
  - живой прогон `ecUpApi` в node: мёртвая сеть обрывается за `EC_UP_IDLE` (~150 мс в тесте),
    медленная сеть с прогрессом доезжает до конца (не убивается сторожем), HTTP-сбой/обрыв
    сети = честный `null`;
  - бэкенд: фото в копилку (JPEG-нормализация, владелец), сборка по id с сохранением порядка,
    чужое/протухшее/неизвестное → `400 gone`, лимит фото, прежний формат работает как раньше.
- Полный прогон `tests/test_*.py` в `dev/` и `prod/` — зелёный (кроме двух прежних падений
  контрактных строк раздела «Материалы» — см. `bug-reports/002`).
- `tests/test_release_contract.py` проходит — копии `dev/` и `prod/` идентичны.

## 6. Что осталось за рамками

- экран проверки после «Готово» идёт долго сам по себе (3–5 минут: OCR до 12 фото + анализ
  Кими) — это ожидаемая длительность пайплайна, она уже честно показывается этапами и
  пульсом (bug-reports/005); ускорение пайплайна — отдельная задача, не баг;
- `api()` с `opt.idle` подключена к запросам «ИИ-проверки»; остальные вызовы `api()` пока
  живут без потолка (длительные — `/api/stt`, `/api/voice` — не должны резаться таймаутом),
  переводить их на потолки — отдельными инцидентами, по мере надобности.
